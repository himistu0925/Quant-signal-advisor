Why

왜 만들었고, 누구에게, 언제 쓰는가

변동성 장세에서 감정적으로 판단하지 않기 위해 시작한 개인 도구다. 실제로 이 도구를 만들기 전, 서로 다른 투자 성향의 페르소나 5명을 세워 가정을 검증해봤는데 (2주차 작업, 아래 참고) — 경력과 무관하게 전원이 매수/매도 타이밍에서 스트레스를 느끼고 있었다.

왜 만들었나

급락·급등장에서 "확신 없이 흔들리는" 순간을 줄이려고. 사람이 확신을 갖는 게 아니라, 지표 근거가 기준을 만족할 때만 후보 신호를 제시하고 최종 실행은 항상 사용자가 한다.

누구에게 쓸모있나

기술적 지표를 신뢰하는 개인 트레이더, 특히 장중 실시간 대응이 어려운 직장인·개발자. 반대로 펀더멘털 중심 장기 가치투자자에게는 이 도구의 전제 자체가 성립하지 않는다는 것도 인터뷰로 확인했다.

어떤 경우에 사용하나

미국 장중(한국 시간 밤~새벽)에 화면을 보고 있을 수 없을 때, 15분마다 자동으로 지표를 점검해 디스코드로 알려준다. 월 1회는 5년치 데이터로 임계값을 재캘리브레이션한다.

확인된 것

  • 경력과 무관하게 전원이 매수/매도 타이밍에서 스트레스를 느낀다 — 단, "매도" 쪽이 더 고통스럽다는 게 공통적으로 나타났다(3명 명시적 언급)
  • 5명 중 4명이 감정/직감보다 지표·데이터 기반 신호를 명확히 선호한다
  • 혼자 판단할 때 흔들리는 이유는 정보 부족이 아니라 판단을 검증해줄 근거(anchor)의 부재 — 지금은 그 자리를 커뮤니티 의견이 대신하고 있고, 종종 틀려서 손실로 이어진다

전제를 수정하게 만든 것

  • 장기 가치투자자(한미영)에게는 "지표 기반 신호 선호" 가정 자체가 성립하지 않는다 — 기술적 지표를 "도박처럼 느껴서" 신뢰하지 않음
  • → 이 도구의 타겟은 "기술적 지표를 신뢰하는 트레이더" 세그먼트로 명확히 한정해야 하며, 펀더멘털 투자자는 애초에 스코프 아웃 유지가 맞다는 걸 재확인
  • plan.md는 매수/매도 신호를 대칭적으로 설계했지만, 실사용자 고통은 매도 쪽에 더 쏠려 있어 매도 신호의 근거 설명을 더 두텁게 만들 필요가 있음 (아직 미착수, 열린 과제)

자세한 질문지·답변 전문은 docs/assumption_validation.md 참고.

2주차 · 기능 확장

진짜 브로커리지 앱처럼

개인용 신호 알림 도구를 넘어, 실제 트레이딩 데스크가 쓸 법한 형태로 세 가지를 더했다.

ATR 기반 리스크 사이징

BUY 신호에 손절/목표가(ATR 배수)와 고정비율 포지션 사이징(거래당 리스크 1%, 종목당 최대 25%)을 자동으로 붙였다. 공개 저장소라 % 기반 값만 대시보드에 남기고, 실제 주식 수는 계산하지 않는다(선택적 비공개 설정, 아직 미사용).

전종목 유니버스 스크리너

미국 상장 종목/ETF 전체(~12,480개)를 매일 밤 유동성 기준으로 스크리닝해 상위 10개 후보를 뽑고, 그 종목이 자기 ATR 대비 2배 이상 급변동하면 실시간으로 알려준다. 워치리스트에는 자동 추가되지 않는다.

대시보드 워치리스트 편집기

"진짜 브로커리지 앱처럼" 티커를 검색해서 직접 추가/삭제하고 싶다는 요구에 맞춰, 별도 백엔드 없이 브라우저에서 GitHub PAT으로 workflow_dispatch API를 직접 호출하는 방식으로 구현했다.

설계가 한 번에 나오지 않은 지점 유니버스 후보 알림은 처음엔 상위 20개를 밤 한 번에 몰아서 디스코드로 보내는 다이제스트 방식으로 만들었다. 실제로 받아보니 "20개를 한 번에 보는 건 실전에 쓸모가 없다"는 게 명확해져서, 상위 10개로 줄이고 "그 종목이 지금 막 크게 움직이는 순간"에만 실시간으로 알리는 방식(detect_sharp_move)으로 갈아엎었다 — 같은 날 안에 뒤집은 설계 변경(commit 37667ae).

시행착오와 배운 점

9일 동안 실제로 24/7 돌려보니, 로컬에서는 안 보이던 운영 이슈가 나왔다. 발견 → 근본 원인 → 조치 순으로 남긴다.

1
GitHub 자체 cron 스케줄러가 발동을 대부분 누락시켰다
schedule.yml이 하루 약 20번 발동해야 하는데 실제로는 2번만 발동. 원인은 GitHub 문서에도 나와 있는 "매 시 정각/30분은 스케줄 부하가 몰려 지연·누락되기 쉽다"는 특성 — :07/:37로 옮겨도 여전히 대부분 누락됐다. 결국 저장소 밖에서 cron-job.org가 workflow_dispatch API를 직접 30분마다 호출하도록 전환하고, GitHub 자체 cron은 백업으로만 남겼다.
